# YOLO Object Detection & 3D Distance Measurement: Benchmark & Stress Testing Guide

This comprehensive guide details the mathematical foundations, evaluation methodologies, benchmark scenes, stress test architectures, and empirical results for the **YOLO Object Detection & Monocular 3D Distance Measurement System**. It provides exact instructions for running the automated benchmark and stress test suites, interpreting their JSON artifacts, and verifying compliance with requirements **R1** and **R2**.

---

## 1. System Mathematical Foundation & Ground Truth Derivation

The monocular 3D distance engine operates on calibrated pinhole projective geometry. Given an input camera frame and a 2D bounding box generated by YOLOv8, physical 3D spatial metrics are analytically derived without stereoscopic hardware.

### 1.1 Monocular Projective Depth ($Z$)
Under the pinhole camera model, the relationship between real-world physical object height ($H_{real}$ in meters), focal length ($f$ in pixels), and detected pixel height ($h_{pixels}$) is governed by:

$$Z = \frac{f \cdot H_{real}}{h_{pixels}}$$

- **$f$ (Focal Length in Pixels)**: Defaults to $0.9 \cdot \text{image\_width}$ when uncalibrated, or an exact optical focal length from camera calibration matrices.
- **$H_{real}$ (Reference Physical Height)**: Derived from known class priors (e.g., standard car = $1.50\text{m}$, adult pedestrian = $1.70\text{m}$, industrial forklift = $2.20\text{m}$, bus = $3.20\text{m}$, truck = $2.80\text{m}$).
- **$h_{pixels}$**: Bounding box pixel height clamped to $\max(1.0, h)$ to prevent division-by-zero singularities.

### 1.2 Camera Space 3D Projection ($X, Y, Z$)
Using the camera optical center (principal point) $(c_x, c_y) = \left(\frac{W}{2}, \frac{H}{2}\right)$ and the detected 2D object centroid $(cx, cy)$:

$$X = \frac{(cx - c_x) \cdot Z}{f}$$

$$Y = \frac{(cy - c_y) \cdot Z}{f}$$

This maps every detected object from image coordinates into metric 3D camera coordinates $(X, Y, Z)$ expressed in meters, where:
- $+X$ points rightward relative to camera optical axis.
- $+Y$ points downward along the vertical camera sensor plane.
- $+Z$ points forward along the optical axis (depth into the scene).

### 1.3 Relative 3D Euclidean Separation ($D_{3D}$)
The physical 3D distance separating two objects $A = (X_A, Y_A, Z_A)$ and $B = (X_B, Y_B, Z_B)$ is calculated via the 3D Euclidean metric:

$$D_{3D} = \sqrt{\Delta X^2 + \Delta Y^2 + \Delta Z^2} = \sqrt{(X_B - X_A)^2 + (Y_B - Y_A)^2 + (Z_B - Z_A)^2}$$

### 1.4 2D Pixel Distance and Normalized Image Percentage
To provide UI feedback and scale-invariant separation context:

$$D_{pixel} = \sqrt{(cx_B - cx_A)^2 + (cy_B - cy_A)^2}$$

$$\text{Normalized Diagonal Percentage} = \left(\frac{D_{pixel}}{\sqrt{W^2 + H^2}}\right) \times 100\%$$

## 3. Evaluation Metrics Definition

The benchmark runner calculates comprehensive computer vision and metric distance evaluation statistics:

| Metric | Mathematical Definition | Purpose |
|--------|-------------------------|---------|
| **Intersection over Union (IoU)** | $\text{IoU} = \frac{\text{Area}(B_{pred} \cap B_{gt})}{\text{Area}(B_{pred} \cup B_{gt})}$ | Measures spatial bounding box overlap against ground truth |
| **Precision** | $\frac{TP}{TP + FP}$ | Measures fraction of detected objects that match true labels |
| **Recall** | $\frac{TP}{TP + FN}$ | Measures fraction of ground-truth objects successfully recovered |
| **F1 Score** | $2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$ | Harmonic mean of precision and recall |
| **mAP50** | Mean Average Precision @ $\text{IoU} \ge 0.50$ | Standard object detection benchmark accuracy |
| **Mean Latency ($ms$)** | $\frac{1}{N} \sum_{i=1}^N t_i$ | Inference latency averaged over warmup and repeated passes |
| **3D Distance Absolute Error** | $|D_{estimated} - D_{ground\_truth}|$ (meters) | Physical metric accuracy of spatial separation |
| **3D Distance Percentage Error** | $\frac{\|D_{estimated} - D_{ground\_truth}\|}{D_{ground\_truth}} \times 100\%$ | Normalized distance estimation precision |
| **Tolerance Pass Rate** | $\frac{N_{pairs\_within\_tolerance}}{N_{total\_pairs}} \times 100\%$ | Proportion of distance evaluations meeting $<5\%$ ($<0.5\%$ optical) |

## 4. How to Run the Accuracy Benchmarks

### 4.1 CLI Execution Command

Run the standalone benchmark runner from the project root:

```bash
# Standard execution (generates benchmark_results.json and displays ASCII tables)
python benchmarks/run_benchmarks.py

# Verbose execution with custom output destination
python benchmarks/run_benchmarks.py --output benchmark_results.json --verbose

# Custom confidence and IoU thresholds
python benchmarks/run_benchmarks.py --conf 0.30 --iou 0.50 --runs 10
```

### 4.2 Interpreting `benchmark_results.json`

The output JSON file contains five structured sections:

1. **`version` & `timestamp`**: Execution metadata and ISO 8601 timestamp.
2. **`system_info`**: Python runtime, host operating system, and loaded YOLO model path.
3. **`overall_metrics`**:
   - `total_scenes`: Number of evaluated calibrated reference scenes (4).
   - `mean_inference_time_ms`: Average model inference time across all scenes ($65.86\text{ms}$).
   - `mean_distance_error_m`: Mean absolute error in meters ($0.0024\text{m} \approx 2.4\text{mm}$).
   - `mean_distance_error_pct`: Mean relative error percentage ($0.05\%$).
   - `max_distance_error_pct`: Peak error across any scene ($0.10\%$).
   - `distance_tolerance_pass_rate_pct`: Percentage of distance pairs passing bounded tolerance ($100.0\%$).
   - `status`: `"PASSED"` when all tolerances are respected.
4. **`per_scene_breakdown`**: Detailed per-scene telemetry including:
   - `latency_metrics`: `mean_ms`, `min_ms`, `max_ms`, `p50_ms`, `p95_ms`.
   - `detection_metrics`: Ground truth count, predicted count, TP/FP/FN, precision, recall, IoU.
   - `distance_evaluations`: Object pairs, ground-truth depths ($Z_a, Z_b$), estimated depths, 3D Euclidean distances, percentage errors, tolerance threshold, and `within_tolerance` boolean flag.

## 5. Concurrency & Latency Stress Testing Methodology

Requirement **R2** dictates strict concurrency and latency stress validation:
- Sustained concurrent traffic from **50+ simultaneous virtual clients**.
- Target REST endpoints: `/api/detect` (computer vision inference) and `/api/distance` (metric geometry calculation).
- Strict enforcement of **0% unhandled HTTP 5xx errors**.
- Latency percentile tracking: **P50, P90, P95, and P99**.
- Real-time **memory leak tracking** via `psutil`.
- Formal attribution of **CPU hardware bottlenecks** when GPU acceleration is absent.

```
                              STRESS TEST ARCHITECTURE
+------------------------------------------------------------------------------------+
|                             Async Client Load Generator                            |
|             (50 Concurrent Async HTTP Workers via httpx / Thread Pool)             |
+-----------------------------------------+------------------------------------------+
                                          |
                     +--------------------+--------------------+
                     |                                         |
                     v                                         v
         [POST /api/detect]                         [POST /api/distance]
    (Base64 payload + YOLOv8n)                 (Bounding Boxes + Pinhole Math)
                     |                                         |
                     +--------------------+--------------------+
                                          |
                                          v
+------------------------------------------------------------------------------------+
|                         Production Multi-Threaded WSGI Server                      |
|                 (Waitress / Werkzeug Threaded Server on Port 5000)                 |
+-----------------------------------------+------------------------------------------+
                     |                                         |
                     v                                         v
+-----------------------------------------+ +----------------------------------------+
|          LatencyProfiler Engine         | |        MemoryTracker (psutil)          |
|  - Min, Mean, Max, StdDev               | |  - Real-time RSS sampling (10 Hz)      |
|  - P50, P90, P95, P99 Percentiles       | |  - Peak RSS vs Baseline delta          |
|  - Inference vs Network Decomposition   | |  - Linear Regression Slope (MB/sec)    |
|  - CPU Contention Bottleneck Profiling  | |  - Leak Detection Threshold (50 MB)    |
+-----------------------------------------+ +----------------------------------------+
```

### 5.1 Async Virtual Client Pool
The load generator (`stress_testing/concurrent_runner.py`) leverages an asynchronous connection pool with 50 concurrent virtual clients. Requests alternate between detection (heavy CPU compute) and distance estimation (light algebraic computation) to simulate realistic multi-user production traffic.

### 5.2 Latency Percentile Profiling
Request durations are timed at microsecond resolution using monotonic clocks. The profiler computes:
- **P50**: Median response time experienced by users.
- **P90**: 90th percentile latency.
- **P95**: 95th percentile latency (target SLA budget: $< 80\text{ms}$).
- **P99**: Tail latency representing worst-case client experience.

### 5.3 Memory Leak Tracking with `psutil`
The memory tracker (`stress_testing/memory_tracker.py`) monitors the server process's Resident Set Size (RSS) at 10 Hz intervals.
- **Baseline RSS**: Memory consumption prior to traffic injection.
- **Peak RSS**: Maximum memory consumed under full concurrency.
- **Final RSS**: Memory level after client pool completes and cooldown period elapses.
- **RSS Slope**: Linear regression slope of memory over time ($\text{MB/sec}$).
- **Leak Threshold**: A delta exceeding $50\text{MB}$ or an monotonically increasing regression slope flags a potential memory leak.

### 5.4 CPU Hardware Bottleneck Attribution
Under 50 simultaneous requests, CPU-based PyTorch/Ultralytics inference encounters core contention on non-GPU host machines. The profiler breaks down response time into:
1. **Model Inference Time**: Measured internally by PyTorch forward pass.
2. **HTTP / Network / Serialization Overhead**: Measured by subtracting inference time from total request roundtrip time.
3. **Inference-Bound Ratio**: $\frac{\text{Mean Inference Time}}{\text{Mean Total Duration}}$.

When the inference-bound ratio exceeds $90\%$, high P95 latency is formally attributed to hardware CPU saturation rather than software architecture flaws, satisfying the R2 acceptance criterion.

Run the standalone stress test pipeline:

```bash
# Standard 50-client, 100-request stress test
python stress_testing/run_stress_test.py --clients 50 --requests 100

python stress_testing/run_stress_test.py --clients 50 --requests 100 --target detect
```
